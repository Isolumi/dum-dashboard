**Imports section:**

```typescript
import { createServerFn } from "@tanstack/react-start";
import { zodValidator } from "@tanstack/zod-adapter";
import { z } from "zod";
import { supabase } from "#/lib/supabase";
import type { Todo } from "#/lib/database.types";
```

**Zod schemas (separate per operation, per Claude's discretion):**

```typescript
const CreateTodoSchema = z.object({
  name: z.string().min(1),
  priority: z.enum(["high", "medium", "low"] as const).default("medium"),
  status: z.enum(["not_started", "started", "complete"] as const).default("not_started"),
  due_date: z.string().date().nullable().optional(),
});

const UpdateTodoSchema = z.object({
  id: z.string().uuid(),
  name: z.string().min(1).optional(),
  priority: z.enum(["high", "medium", "low"] as const).optional(),
  status: z.enum(["not_started", "started", "complete"] as const).optional(),
  due_date: z.string().date().nullable().optional(),
});

const DeleteTodoSchema = z.object({
  id: z.string().uuid(),
});

const GetTodoSchema = z.object({
  id: z.string().uuid(),
});
```

Use `z.object()` (NOT `z.looseObject()`) to avoid Zod v4 type conflict with createServerFn internals (Pitfall 6 from research).

**Server functions:**

1. `getTodos` -- GET, no input, returns `Todo[]` ordered by `created_at` descending:
```typescript
export const getTodos = createServerFn({ method: "GET" }).handler(
  async () => {
    const { data, error } = await supabase
      .from("todos")
      .select("*")
      .order("created_at", { ascending: false });
    if (error) throw new Error(`Failed to fetch todos: ${error.message}`);
    return data;
  },
);
```

2. `getTodo` -- GET, input `{ id: string }`, returns single `Todo`:
```typescript
export const getTodo = createServerFn({ method: "GET" })
  .inputValidator(zodValidator(GetTodoSchema))
  .handler(async ({ data }) => {
    const { data: todo, error } = await supabase
      .from("todos")
      .select("*")
      .eq("id", data.id)
      .single();
    if (error) throw new Error(`Failed to fetch todo: ${error.message}`);
    return todo;
  });
```

3. `createTodo` -- POST, input validated by CreateTodoSchema, returns created `Todo`:
```typescript
export const createTodo = createServerFn({ method: "POST" })
  .inputValidator(zodValidator(CreateTodoSchema))
  .handler(async ({ data }) => {
    const { data: todo, error } = await supabase
      .from("todos")
      .insert(data)
      .select()
      .single();
    if (error) throw new Error(`Failed to create todo: ${error.message}`);
    return todo;
  });
```

4. `updateTodo` -- POST, input validated by UpdateTodoSchema (id required, other fields optional), returns updated `Todo`:
```typescript
export const updateTodo = createServerFn({ method: "POST" })
  .inputValidator(zodValidator(UpdateTodoSchema))
  .handler(async ({ data }) => {
    const { id, ...fields } = data;
    const { data: todo, error } = await supabase
      .from("todos")
      .update(fields)
      .eq("id", id)
      .select()
      .single();
    if (error) throw new Error(`Failed to update todo: ${error.message}`);
    return todo;
  });
```

5. `deleteTodo` -- POST, input `{ id: string }`, returns void (no data returned):
```typescript
export const deleteTodo = createServerFn({ method: "POST" })
  .inputValidator(zodValidator(DeleteTodoSchema))
  .handler(async ({ data }) => {
    const { error } = await supabase.from("todos").delete().eq("id", data.id);
    if (error) throw new Error(`Failed to delete todo: ${error.message}`);
  });
```

**Important patterns:**
- All mutations use `method: "POST"`, reads use `method: "GET"` (per research recommendation)
- All Zod schemas pass through `zodValidator()` from `@tanstack/zod-adapter` -- NEVER pass raw Zod schema to `.inputValidator()` (Pitfall 2)
- Error handling: throw on Supabase errors, let TanStack Start error boundaries handle them (per research recommendation)
- `supabase` imported from `#/lib/supabase` -- this import is inside a `createServerFn` handler so the compiler strips it from client bundles
- The `Todo` type import is used only for documentation/readability -- the actual return types are inferred from Supabase's `select()` calls
