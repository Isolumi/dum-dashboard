# Buy list implementation plan

> Execute with subagent-driven-development. The controller owns infrastructure validation and deployment.

**Goal:** A name-only Buy list with add, rename, and delete in the Overview and a dedicated page.
**Architecture:** Server-only Supabase CRUD, a polling optimistic controller, and one shared React list.
**Stack:** Existing TanStack Start, React, Tailwind, Base UI, Lucide, Zod, Supabase, Vitest, OXC.
**Spec:** `docs/superpowers/specs/2026-09-17-buy-list-design.md`

## Global Constraints

- Item names only. Add, rename, and delete items.
- Label: Buy list. Route: `/buy-list`.
- Place the Overview card below Calendar in the wide left column. Do not move existing cards.
- Use one shared list component for both views; all three actions work in either view.
- A single inline input adds an item with Enter or an Add button.
- Click an item name to rename it. Enter saves; Escape cancels.
- Keep item text left-aligned and allow wrapping. Show `No items` when empty.
- List newest items first; renaming does not change their position.
- Refresh automatically every 10 seconds. Initial-load failure has a retry control; refresh failure keeps existing items visible.
- No changes to Todos, Jobs, Monies, Uwumi, the MCP API, or login.
- Add the schema before publishing the application image. Do not change existing tables or user records.
- No new runtime dependency.

### Task 1: Build the complete Buy list slice

**Files:**

- Create `supabase/migrations/<CLI timestamp>_create_buy_list_items.sql` using `bunx supabase migration new create_buy_list_items` before apply_patch.
- Create `supabase/tests/database/buy_list_items.test.sql`.
- Extend `src/lib/database.types.ts` with public.buy_list_items and BuyListItem type.
- Create `src/routes/buy-list/buy-list.schemas.ts`, `buy-list.domain.ts`, `buy-list.functions.ts` and their ignored `-*.test.ts` files.
- Create `src/routes/_layout/buy-list/-useBuyListController.ts`, `-BuyList.tsx`, `-BuyListBentoCard.tsx`, `index.tsx` and ignored controller/component tests.
- Modify `src/tools/registry.ts`, `src/routes/_layout/index.tsx`, Overview/registry tests and `vitest.config.ts` only for this feature.
- Regenerate `src/routeTree.gen.ts` through existing build; do not hand-edit it.

**Interfaces:**
`BuyListItem = {id:string; name:string; created_at:string}`.
Server functions `getBuyList()`, `createBuyListItem({data:{name}})`, `renameBuyListItem({data:{id,name}})`, `deleteBuyListItem({data:{id}})`.
Controller returns items, loading/error status, refresh, add/rename/remove, pending IDs and safe mutation error. Mutation promises report success so the UI retains failed drafts.
Shared BuyList receives the controller and compact boolean; both routes render it.

**Step 1 — RED:** Write schema validation, domain query, server boundary, controller and component tests first. Run focused Vitest tests and record expected failures from absent modules/features. Include trimmed 1–300 chars, invalid UUID, same-origin/owner/no-store, safe missing-item/database errors; optimistic create/rename/delete; independent concurrent writes with targeted rollback; stale refresh begun before/during mutation; duplicate same-item writes; initial retry; refresh retention; 10-second polling; add keyboard and failed draft retention; rename Enter/Escape; delete hover/focus/touch; wrapping and empty state; Overview placement and sidebar route.

**Step 2 — schema/domain:** Table definition:

```sql
create table public.buy_list_items (
 id uuid primary key default gen_random_uuid(),
 name text not null check (name = btrim(name) and char_length(name) between 1 and 300),
 created_at timestamptz not null default now()
);
create index buy_list_items_created_at_id_desc_idx on public.buy_list_items (created_at desc, id desc);
alter table public.buy_list_items enable row level security;
revoke all on public.buy_list_items from anon, authenticated;
grant select, insert, update, delete on public.buy_list_items to service_role;
```

Use existing admin client; descending created_at/id order, retain created_at on rename, selected canonical records after writes, not-found errors for absent records. No arbitrary small truncation of the saved list. Database tests cover checks, index, RLS, denied direct roles, service CRUD and preserved creation timestamp.

**Step 3 — server/controller:** Reuse owner, noStore, assertSameOrigin and strict Zod patterns. Generic safe UI errors, no secret/raw database exception leakage. Use existing polling hook. Optimistic temporary IDs are not writable until creation completes. Block duplicate writes to a pending item. Invalidate reads at mutation start/end; do not let stale polls overwrite pending UI. Roll back only the affected item, not snapshots of the whole list. Distinct simultaneous item mutations remain supported.

**Step 4 — UI:** Existing palette and controls only, ShoppingBag Lucide icon. Shared left-aligned wrapping list with compact delete buttons, inline rename and one add form. No additional fields. Page follows existing Jobs page shell. Bento title links to /buy-list; bounded max-height scroll for long lists. Place registry entry after Calendar and include it in primary Overview filtering without touching existing side order. Register server tests in both Vitest exclusion and server-unit inclusion patterns.

**Step 5 — GREEN:** Run focused tests while iterating, then full `bun run test`, `bun run lint`, `bun run build`, and formatting check before committing. If existing Docker-backed tests are unavailable because local Docker is stopped, report exact blocked tests; do not start Docker or remove those tests. CI will run them. Inspect own diff for scope and missing cases.

**Step 6 — commit/report:** Commit scoped changes, with complete RED/GREEN evidence and changed files in task report. No external writes, production SQL, push/PR/merge/deploy or subagents. Controller handles real database tests, independent reviews and publication.
